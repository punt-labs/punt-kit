## Packaging, scopes, and installation

Official packaging guidance prefers portable root manifests. Inline `extensions.com.openai` takes precedence over the entire compatibility overlay; they do not merge. Portable component discovery comes from `skills/` and `mcp.json`, while legacy `skills`/`mcpServers` declarations do not override portable components. Catalog locations are `.agents/plugins/marketplace.json` in a repository or user directory. Catalog paths resolve against the marketplace root. Git, local, and npm sources exist. Installed copies are cached. Repository `.codex/config.toml` controls local-marketplace plugin enablement for trusted projects. Refresh can fetch disabled plugin files. Public-directory submission has different hosting requirements from local distribution. [Package your plugin](https://developers.openai.com/plugins/build/plugins).

Recommended Punt contract:

1. Version each product's native plugin alongside its core release; release metadata records supported Codex versions and adapter protocol versions.
2. Maintain one curated Punt marketplace. Repository installation is not equivalent to per-repository product enablement: product-level `enabled` state must be checked by tools and hooks.
3. Use `PLUGIN_ROOT` for immutable package assets and `PLUGIN_DATA` for host-provided writable plugin state. Avoid `CLAUDE_PLUGIN_ROOT`, cache-path guessing, repository-relative launch assumptions, and files written into plugin caches.
4. Separate runtime dependency installation from marketplace registration. Do not rely on npm install scripts to provision Python binaries or services. Provide an explicit doctor/check command that verifies CLI resolution, pinned runtime compatibility, transports, and renderer/audio dependencies.
5. Upgrades must test installed cache refresh, restarted sessions, changed hook trust, and mixed core/adapter versions. Removal cleans owned registrations and workers; it preserves user content and unrelated settings.
6. Use stock CLI plugin commands for CLI setup; the local help proves native add/remove support even though portions of current packaging prose still emphasize desktop installation.

## MCP and configuration

Local Codex clients share host MCP configuration, supporting stdio with environment/cwd settings and Streamable HTTP with bearer/OAuth authentication. Server initialization instructions are read by Codex. Per-server startup/tool timeouts, required initialization, enablement, tool allow/deny lists, and per-tool approval policy are documented. Plugin MCP policy has its own `plugins.<plugin>.mcp_servers.<server>` scope. Tool `readOnlyHint` matters when users choose `writes` approval behavior. [MCP](https://learn.chatgpt.com/docs/extend/mcp).

Product work should include correct annotations, strict structured arguments/results, cancellation, errors, bounded output, and readiness reporting. Long-running operations should expose durable job handles and status rather than keeping one invocation open indefinitely. Servers must resolve the intended workspace explicitly and reject ambiguous stateful calls. Do not mark write/send tools read-only merely to reduce prompts.

Configuration has user, project, and managed layers; project files require trust. Project-local routing keys including `notify` are ignored. Native TUI status configuration selects item identifiers rather than declaring arbitrary shell providers. [Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). A shared generated configuration writer should preserve comments/unrelated settings and make enablement changes idempotent. Native approval UX should retain the user's actual permission choices.

## Hooks: supported contract and critical differences

Supported events: SessionStart, SessionEnd, SubagentStart, SubagentStop, UserPromptSubmit, PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact, Stop, Interrupt. Command and MCP handlers work; prompt/agent handlers are skipped. Hook trust uses the definition hash. Concurrent matching hooks all start. Inputs include session_id/cwd; subagent lifecycle adds agent_id; transcripts are unstable. PreToolUse can deny or rewrite arguments; `ask` is unsupported. PostToolUse cannot undo effects or use updatedMCPToolOutput. Hosted tools and write_stdin lack complete interception. Stop can request continuation. Async completion never starts an idle turn. SessionEnd is advisory, short-lived, and excludes subagents. MCP hooks require existing connections, fail open on availability errors, and cannot handle SessionEnd. [Hooks](https://learn.chatgpt.com/docs/hooks).

Adapter implementation requirements and probes:

- Parse real Codex event fixtures; never rename Claude handlers and assume JSON parity. Handle missing transcript paths and nullable latest assistant output.
- For Bash/apply_patch, assert actual canonical names and input shape; exercise `exec_command` finishing through a later `write_stdin` poll. Match nested code-mode calls too.
- Require synchronous execution for decisions; use asynchronous work only for informational feedback. Serialize or deduplicate product state explicitly because independent hook invocations can finish out of order.
- Treat all hook effects as idempotent. Startup, resume, clear, compaction, overlapping subagents, and shutdown may all interact with the same core service.
- Register/session refresh and compaction recovery should rehydrate durable product state; identity must never depend on a one-time prompt surviving forever.
- Keep final-output recording, audio enqueue, and bounded cleanup fast. Long work goes to a product-owned durable queue. Give workers lease expiry because abrupt exits do not guarantee cleanup.
- A disabled, untrusted, changed, missing, crashed, or timed-out guard must be visible to product doctor and must not cause the core to accept an unauthenticated stateful operation. Treat core enforcement and optional harness feedback as distinct responsibilities.
- Use bounded Stop continuation and test loops explicitly. Do not repurpose the session lifetime as a permanent receive daemon.

## Authoritative session propagation: mandatory spike

The research does **not** establish that a SessionStart hook can modify the parent shell environment, export values into a subsequently launched MCP process, or attach authoritative per-call thread metadata to every MCP request. Static MCP env/env_vars/cwd settings are documented; they are not proof of per-thread identity. The public environment-variable page describes variables Codex reads, not a guarantee of exported child session identity. [Environment variables](https://learn.chatgpt.com/docs/config-file/environment-variables).

App-server startup notifications can be app-scoped with a null threadId. Therefore a one-MCP-child-per-thread assumption is unsafe without direct release verification. Default generated ThreadStartParams has no dedicated MCP session-metadata field. Experimental dynamic tools provide a host integration path but change the hosting boundary. [App Server](https://learn.chatgpt.com/docs/app-server), [local ThreadStartParams](codex-sources/schema-stable/v2/ThreadStartParams.json).

Plan a common Codex context transport spike owned by punt-kit with ethos, biff, vox, and lux consumers:

1. Launch two stock Codex threads in one repo, two repos, and two worktrees; add subagents and concurrent calls. Probe what the actual MCP invocation and launched CLI can observe. Record which identifiers are root, child, turn, and tool-call scoped.
2. Test resume, fork, clear, compaction, change of cwd, desktop shared daemon, and CLI reconnect. Assert no cross-session identity, inbox, audio queue, or renderer ownership leaks.
3. Evaluate a supported native per-call channel first. A candidate is synchronous hook-owned context injection through updatedInput, backed by an authenticated product adapter; the core must verify the context and reject missing/stale/forged binding. This is a proposal, not a validated security design. Model-authored `session_id` values must never confer authority.
4. If a channel is unavailable, scope the affected feature honestly and create a precise upstream capability request or explicit custom-host integration epic. Do not fall back to process ancestry, parent environment mutation, transcript scraping, or one global active-session file.

Identity is not authorization. Ethos should distinguish authenticated principal, claimed display name, harness session, delegated actor, project, and operation grants in its own protocol regardless of harness.

## Biff push delivery and existing-bead amendments

`codex queue --help` proves native submission by session UUID or exact session name. It exposes `--message`, remote endpoint flags, and many session/config flags. No message-id or JSON-result switch is present in help. Do not infer permission inheritance merely because flags appear.

Schema generation gives stronger maturity evidence: `thread/queue/add`, `/list`, `/update`, `/delete`, `/reorder`, and `/start` are absent from default ClientRequest and present only with `--experimental`. Add requires `threadId`, `clientUserMessageId`, and `input`; Start takes `threadId` and optional queuedSubmissionId and returns a turn. A distinct start method means automatic idle consumption cannot be assumed. The fetched public CLI/app-server pages did not document the command's queue semantics. [Installed CLI evidence](codex-sources/installed-cli-evidence.json), [experimental Add](codex-sources/schema-experimental/v2/ThreadQueueAddParams.json), [experimental Start](codex-sources/schema-experimental/v2/ThreadQueueStartParams.json).

Amend **biff-lp5r** to retain a native queue-worker design as the preferred candidate, adding a release-blocking verification task before claiming push parity. **biff-6vvo** should expose Biff-owned durable events/JSONL, not tail Codex transcripts. Suggested flow: product-owned authenticated subscription -> durable cursor/dedup -> exact native thread binding -> stock queue submission -> explicit delivery acknowledgement. This extends Codex through its interface and does not wrap its TUI.

Required probes: idle/busy delivery; enqueue versus automatic start; interruption/resume; closed/archived/deleted/unknown thread; ambiguous exact names; daemon restart; plugin disable/remove; retried delivery; preserving original sandbox/approval/repo settings; user cancellation; incoming text containing instructions; subagent routing; worker crashes between submission and acknowledgement. Use exact registered IDs, no guessed names. If CLI cannot provide reliable dedup/acknowledgement, evaluate its experimental typed protocol separately and declare that compatibility boundary. Biff-owned incoming content must remain attributable message data rather than being silently treated as new user authorization.

## Skills, commands, agents, and UI

Native skills use name/description plus SKILL.md, optional resources/scripts and agents/openai.yaml. Explicit invocation uses `$` or `/skills`; implicit matching can be disabled with allow_implicit_invocation. Local repository discovery uses `.agents/skills`, and plugins are the distribution mechanism. [Build skills](https://learn.chatgpt.com/docs/build-skills).

AGENTS.md is loaded by an instruction hierarchy with override files and a size limit; it is not a runtime enforcement layer. [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md).

Custom agents are native TOML in `.codex/agents/` or `~/.codex/agents/`, requiring name, description, and developer_instructions; they can configure model/sandbox/MCP. Subagent behavior is available in current local clients, with delegation requested by user or applicable instructions. [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).

For prfaq/z-spec, share semantic workflow content but author native role selection, tool invocation, output artifacts, interruption, and delegated-result handling. Do not assume Claude command frontmatter or agent packaging has matching semantics. No plugin-bundled custom-agent directory discovery was established: initially have skills delegate explicit bounded roles, or install reviewed project agent TOML through an owned setup path after testing.

For Biff, a configurable footer is not evidence of third-party badge widgets. Prefer actual native messages, tool output, and verified queued delivery; make a persistent native badge an upstream issue if required. For Lux, make its own renderer and MCP contract excellent independently of host widgets. Optional MCP UI uses the MCP Apps bridge with OpenAI additions, but host availability differs; local `enable_mcp_apps` is currently under development. [Optional plugin UI](https://developers.openai.com/plugins/build/chatgpt-ui). For Vox, explicit MCP/CLI audio actions and product-owned playback queues are viable; test actual image/audio attachment presentation separately from producing files. Never assume generic MCP audio output automatically speaks in every client.

## Stock integrations versus embedding

The SDK provides application-controlled threads; TypeScript and Python libraries are documented, and Python pins a runtime dependency. App Server is for clients owning authentication, history, approvals, and events. `codex mcp-server` has been removed. [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk).

App-server `dynamicTools` and item/tool/call are experimental. The generated default ThreadStartParams omits dynamicTools. WebSocket transport is explicitly experimental/unsupported in current prose, while stdio and Unix socket forms are documented. The CLI still labels app-server experimental. [App Server](https://learn.chatgpt.com/docs/app-server).

Use SDK/App Server when a Punt product intentionally controls a Codex worker or offers an independent host. Do not make that a prerequisite for ordinary installation in stock Codex, and do not describe custom-host-only capabilities as stock plugin features. Hook/native queue support makes a wrapper unnecessary for many lifecycle features; remaining unsupported behavior should produce concrete upstream work.

## Implementation sequencing and release acceptance

**C1, native host contract** — punt-kit owns supported release matrix, capability schema, plugin/catalog validation, context transport spike, hook fixtures, and installation ownership. Blocking defects discovered in each product become product-core tasks, even if remediation is a substantial refactor.

**C2, representative pilots** — a stateless/read-oriented MCP + skill product; Biff lifecycle/push; Ethos context/authority; Lux/Vox client/renderer/audio. Use these to validate design contracts before nine repetitive adapters are produced.

**C3, repository delivery** — each product owns core fixes, native package, workflow content, hook implementation where needed, docs, upgrade/removal, and end-to-end tests. Beadle must preserve send authorization independently of incoming notifications; Quarry needs durable context/capture APIs; punt-kit standards must enforce all these changes rather than preserving Claude assumptions.

**C4, complete user journey** — install from an empty supported host; inspect and trust hooks; enable one repository; invoke native workflows/tools; exercise actual product outcome; resume/compact; test concurrency; restart/upgrade; disable; uninstall. Assert no Claude executable/config/plugin directory is needed. Assert the product's normal CLI/HTTP/MCP remains usable and coherent. No successful catalog listing alone counts as completion.

Publish a capability matrix per **client surface and version**, distinguishing supported native behavior, explicitly experimental behavior, and unresolved gaps. Include plain error/doctor output when a required capability is absent. A native-looking install with an unverified identity channel or nonfunctional idle receive is not complete support.
