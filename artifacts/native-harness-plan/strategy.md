# OpenCode first, pi second, Codex deferred

Research synthesis and execution rationale • operator decision 2026-09-13 • technical evidence audited 2026-09-12

**OpenCode is P1, pi coding agent is P2, and Codex is deferred for now.** Apply that order to each product's native integration and to the associated worker, voice-control, packaging and certification work. Shared product repairs needed by OpenCode are P1. Pi-specific machinery is P2. Retain the Codex research and proposed work for later reassessment, with no Codex experiment or release outcome blocking either active harness.

This changes execution priority, not the intended quality of support. OpenCode and pi still require their own native packages, lifecycle behavior, permissions and complete product journeys. The active program has eighteen product–harness outcomes: nine OpenCode outcomes first, nine pi outcomes second. The nine Codex outcomes remain documented deferred work. Existing Claude integration remains a regression obligation while product engines change.

This writeup uses the September 12 source audit and fetched upstream evidence. It introduces no claim that a model session, mailbox, display, audio device or new adapter was tested. The original certification candidates remain OpenCode 1.18.30, with installed 1.18.27 as a compatibility candidate, and pi 0.85.1, with installed 0.84.4 as a separately evaluated compatibility candidate. Recheck those candidates when implementation starts. [OpenCode evidence](harnesses/opencode.md), [pi evidence](harnesses/pi.md), [source baseline](evidence/source-baseline.json).

## Why OpenCode is the right first implementation

The operator chose the order. The audited architecture supports that choice for five concrete reasons.

**1. Stateful calls have a native source of session identity.** OpenCode custom tools receive the real session ID and agent context, while a server plugin knows its directory/worktree and can query SDK session metadata for lineage. That gives Biff presence, Beadle account selection, Vox voice preferences, Lux scene ownership, Quarry database selection and Ethos mission binding a direct path into the product engine. Use native typed tools for these calls; sharing an MCP process must not collapse multiple conversations into one mutable “current session.” This is a supported native entry point, although the actual trust binding and lifecycle still need executable tests. [Tool interface](https://github.com/anomalyco/opencode/blob/3104c1428ec91f809e5ab86631300de41eb6952e/packages/plugin/src/tool.ts), [shared context design](architecture.md#2-explicit-context-and-authoritative-state).

OpenCode's shared-server architecture also provides an effective early test of the toolkit's boundaries. A Biff `ServerState` owns one tty; Beadle's identity override assumes a process equals a session; Vox keeps session preferences in its MCP process; Quarry's selected database is a client-process singleton. Merely giving those objects an OpenCode-shaped wrapper would reproduce known defects. Two simultaneous native sessions force the implementation to put state in the appropriate product service and carry explicit context on every operation. Pi can then use those repaired services without repeating the migration. [Biff](repos/biff.md), [Beadle](repos/beadle.md), [Vox](repos/vox.md), [Quarry](repos/quarry.md).

**2. Background delivery has credible native mechanisms.** OpenCode offers session-scoped SDK prompts, asynchronous prompts, persisted input without starting a reply, and incoming-message hooks. These are better foundations for Biff receive and Beadle inbox awareness than the experimental transcript transform proposed in older Biff work. They also support Lux interactions that require model work and Vox's controlled steering experiments. A 204 response only proves acceptance by an endpoint; the initial host experiment must establish persistence, busy-session behavior, loop completion races, cancellation, receipt semantics and deduplication. Never await a running same-session prompt from an awaited tool hook. [Prompt implementation](https://github.com/anomalyco/opencode/blob/3104c1428ec91f809e5ab86631300de41eb6952e/packages/opencode/src/session/prompt.ts), [delivery analysis](harnesses/opencode.md#biffbeadle-inbox-stable-delivery-and-reentrancy).

**3. Native UI and lifecycle are substantial enough for the toolkit.** The released package exposes server hooks/tools and a separate TUI interface with status slots, dialogs, keymaps, attention and disposal. That fits Biff unread status, Ethos persona/mission status, Vox controls, Lux connection controls and task progress. Server `dispose` and TUI disposal are distinct; closing an attached TUI must not incorrectly end a server-owned session. Lux still renders rich visuals, and Vox still owns actual speech/music/audio routing. A server on another machine does not make its audio device the user's desired device. These APIs reduce the need for host-specific workarounds while preserving the products' own rendering engines. [Plugin interface](https://github.com/anomalyco/opencode/blob/3104c1428ec91f809e5ab86631300de41eb6952e/packages/plugin/src/index.ts), [TUI interface](https://github.com/anomalyco/opencode/blob/3104c1428ec91f809e5ab86631300de41eb6952e/packages/plugin/src/tui.ts).

**4. Independent reviewers can use existing native delegation.** PRFAQ meetings, Z-spec audits, Ethos evaluators and Punt's judgment auditor require separate agent contexts and attributable results. OpenCode already has named agents, task delegation and child sessions. Each workflow still needs correct role prompts, grants, completion/cancellation handling and durable evidence, but the stock harness supplies the underlying delegation path. Pi supplies powerful extension and SDK APIs but no stock subagent facility: the P2 program must deliver and maintain an explicit bounded child-session supervisor. That is useful engineering, but it is additional implementation and validation work before Pi can complete these workflows. [OpenCode agent documentation](https://opencode.ai/docs/agents/), [PRFAQ plan](repos/prfaq.md), [pi delegation analysis](harnesses/pi.md).

**5. The first implementation can establish reusable product contracts without inventing a universal harness layer.** OpenCode and pi both accept TypeScript native integration code, so a product's typed HTTP/WS client, result validator or bounded subprocess helper may be reusable. Their event models, tool APIs, UI and delegation semantics remain different. Share a Lux wire client or Quarry capture schema; independently implement the OpenCode server/TUI lifecycle and pi extension lifecycle. Validate reuse in two concrete adapters before extracting a toolkit-wide helper package. [Architecture ownership](architecture.md#1-product-core-native-adapter-and-distribution-are-different-things).

This choice does not establish universal OpenCode enforcement or guaranteed delivery. Source inspection found that `permission.ask` is declared but uninvoked, generic event callbacks are unawaited, plugin load failures can be logged and ignored, and experimental code-mode needs separate gate coverage. The native before-tool hook is a useful enforceable boundary for covered model calls; it is not OS containment or a replacement for Beadle/Biff domain authorization. P1 includes proving these limits and making activation failures visible. [Gate/runtime findings](harnesses/opencode.md#lifecycle-gates-and-identity-details-that-affect-correctness).

## How to interpret complexity

Count three different things: **shared remediation**, **incremental native adapter work**, and **delivery risk**. Publishing an npm package may be small while the complete product remains difficult. A state migration is paid once per product; it should not be estimated again as “OpenCode implementation” and “pi implementation.” Conversely, a shared protocol does not make the second adapter free.

The comparative ranking discussed with the operator is recorded here on a **1–5 relative-complexity scale**, with 5 highest. These are judgments, not elapsed-time estimates or an arithmetic cost model. Shared remediation is counted once. Codex scores are historical context only; no Codex effort is allocated to P1/P2.

An asterisk marks an unproven native capability in the original Codex analysis, principally authoritative context, delivery or capture. **Beadle and Biff are the largest overall product lifts; Ethos and Vox form the next group.** Quarry's capture is harder than its retrieval; PRFAQ's orchestration is harder than its deterministic helpers; Z-spec's correctness is harder than tool registration. Lux is the best existing architectural foundation for an early stateful pilot. Punt's own adapters are comparatively small, but its program-wide standards/release responsibilities are substantial.

Pi's relative difficulty rises for independent-review workflows because a real child supervisor must be delivered once and reused. ## P1 rollout: release OpenCode in dependency order

The sequence below names existing planning keys. It does not create new Beads, supersede product epics or prescribe a single serial team. Independent core work proceeds concurrently; each release waits only for the prerequisites its actual journey needs.

### Stage 1 — certify one native package and the risky host behaviors

Start `KIT-PROGRAM`, the first `KIT-STD` contracts, `KIT-RESULT`, `KIT-CONTENT`, the necessary `KIT-RELEASE` work and `HOST-OPENCODE`. The first vertical slice is one deterministic Punt operation from a versioned native package installed outside the checkout, with Claude absent. Demonstrate structured success and failure, native discovery, selected repo enablement, update and exact owned removal. Follow with the broader `KIT-OPENCODE` work; the pilot does not claim the full judgment auditor has shipped.

In the same host experiment, use a disposable contextual test service to validate two server sessions, child sessions, two worktrees, native permission denial, gate activation, TUI attach/detach, server disposal and process crash. Exercise authorized input persistence/wake while idle and busy, including the final-loop race. Distinguish accepted, persisted, started, consumed and uncertain outcomes. That experiment may use synthetic fixture events; shipping Biff injection still requires Biff authenticity and recipient policy.

Pass artifacts are exact core/package/harness versions, clean-install transcripts, context/lifecycle traces, a tested event-drain pattern and a stated gate coverage matrix. A missing optional UI feature can remain optional; a missing required identity/delivery boundary blocks that feature. No Codex package/context/queue probe participates in this stage.

### Stage 2 — fix shared engines and validate representative OpenCode slices

Run these independent tracks against the pinned context/result/install contracts:

- **Identity:** `ETHOS-CONTEXT`, `ETHOS-SERVICE`, `ETHOS-GOVERNANCE` and `ETHOS-PERSONAS` feed `ETHOS-OPENCODE`. Prove two native sessions plus two same-persona children remain distinct and record results correctly. Schedule `ETHOS-AUTHORITY` separately but at P1 because Biff M2 requires it.
- **Messaging:** `BIFF-DESIGN`, `BIFF-CORE`, `BIFF-EVENTS`, Claude parity, `BIFF-AUTH` and `BIFF-POLICY` feed `BIFF-OPENCODE`. Tool registration/presence prototypes can begin while signature work proceeds. Native automatic content delivery cannot ship ahead of the existing biff-00v M2/M3 requirements.
- **Mail:** `BEADLE-MAIL`, `BEADLE-SESSION`, `BEADLE-RECEIVE` feed `BEADLE-OPENCODE`. Verify denied reads/writes and correct account scope through every public client before native use. Inbox watching remains separate from starting the execution daemon.
- **Media:** `VOX-DESIGN`, `VOX-STATE`, `VOX-CONTRACT`, `VOX-ENABLE` feed `VOX-OPENCODE`; `LUX-CONTEXT`, `LUX-LIFETIME`, `LUX-ENABLE`, `LUX-CLIENT` feed `LUX-OPENCODE`. Observe finite speech/stop/preferences and a real scene/callback before adding richer controls. Each owns its own release; optional peer absence remains usable.
- **Knowledge:** `QUARRY-DESIGN`, `QUARRY-CONTEXT`, `QUARRY-SURFACE`, `QUARRY-ENABLE` establish native retrieval with an explicit target; `QUARRY-CAPTURE` completes `QUARRY-OPENCODE`'s capture journey. SDK snapshots feed the neutral capture service, never a forged Claude transcript.
- **Workflows:** `PRFAQ-CLI`, `PRFAQ-MEETING`, `PRFAQ-RESEARCH` and Z-spec correctness/execution/context/workflow work progress alongside the services. These do not need to wait for a complete Biff release. Correct solver evidence and packaged meeting state are valuable before native orchestration is complete.

Biff's default acceptance is specific: trusted messages produce attributed full-content injection; verified and unsigned/unverified messages produce wake-only prompts; failed signatures produce warnings with no injection. Configuration may tighten trusted delivery or widen verified delivery, but cannot grant full-content injection to unverified/untrusted messages. Include forward with preserved signed payloads and minimum trust across the chain, on all required public surfaces in the coordinated release. These are operator requirements, not optional adapter preferences. [Biff requirements](https://github.com/punt-labs/biff/blob/fdf49f322a58ac04d4c55200b8f22d254889c27f/docs/requirements-biffd-multihost.md#L194).

The first releases can expose completed bounded capabilities with precise status. An OpenCode search tool is a useful release while capture remains in progress; it does not close the full Quarry cell. Finite Vox speech can ship while controlled voice remains in progress; it does not silently satisfy that distinct journey. Record these sub-outcomes in the acceptance ledger so priority does not become pressure to overstate completion.

### Stage 3 — complete OpenCode workflows and controlled execution

Finish `PRFAQ-OPENCODE`, `ZSPEC-OPENCODE`, `KIT-AUDITOR` and Ethos's independent evaluation journey using actual native child sessions, separate role evidence and cancellation. Package every workflow resource. PRFAQ questions that have not been answered remain pending; a headless path needs explicit decisions or a resumable pause, never an invented human choice. A Z-spec solver or reviewer result carries actual evidence and completeness.

Run **Beadle OpenCode workers** as a separately visible P1 outcome: `BEADLE-WORKER-CONTRACT` → `BEADLE-SUPERVISOR` → `BEADLE-WORKER-OPENCODE`. Version signed recipe/grant semantics, implement real containment and credential scope, preserve GPG/x-bit admission, claim jobs durably and make the supervisor record validated results and mission finalization. Current headless behavior must use verified flags and explicit permissions: `-p` is password, unsupported Claude-like tool flags are not a plan, and auto-rejecting prompts does not constrain otherwise allowed operations. Test the real signed-mail→native worker→result→mission-close→reply chain, with budgets, cancellation and failure outcomes. [Beadle worker design](repos/beadle.md#native-unattended-workers).

Run **Vox OpenCode controlled voice** through `VOX-DESIGN` and the OpenCode portion of `VOX-CALL`: reconcile existing voice decisions, then prove supported launch/attach/steer/interrupt, explicit session destination, credential/read scope and audio host. Existing historical pi experiments remain design evidence; they do not put a pi backend back on the P1 delivery path. No TTY injection substitutes for a supported session channel. The chosen voice architecture and its upstream limitations may make this one of the last OpenCode outcomes to certify.

### Stage 4 — certify and release all nine OpenCode products together

Each repository owns its OpenCode artifact, migrations, doctor, version compatibility, native permission/lifecycle tests and observable product journey. `KIT-CONFORMANCE` defines the evidence format; `KIT-FLEET` tests composition. Install all nine from their final artifacts, check command/tool/status collisions and prompt load, run concurrent sessions/worktrees, remove one adapter with others active, and exercise absent/disabled peers. Verify real consumed inbox turns, audible playback, painted display/click responses and independent reviewers where promised. Preserve current Claude regression journeys throughout.

P1 completion means nine certified OpenCode product outcomes, with required Beadle worker and Vox controlled-voice sub-outcomes explicitly tracked and resolved. It does not mean every unrelated optional future feature in every repository is complete. Common release tasks must be splittable by target; a deferred Codex row cannot keep an OpenCode release administratively blocked.

## P2 rollout: implement pi on the repaired product contracts

Pi is the second native implementation and an important test that the new services are genuinely harness-independent. Carry forward the product context schemas, operation results, authorization, durable event feeds, capture model, meeting state, solver runner, signed worker contract, installed assets and release evidence format. Do not carry forward OpenCode hook payloads, SDK sessions, permission assumptions or TUI registration objects.

Start `HOST-PI` and the pi portion of `KIT-PI` with the same finite operation/package exercise. Validate current released package APIs and the real lifecycle: allocate resources at `session_start`, stop them on `session_shutdown`, handle same-runtime tree navigation separately, guard late callbacks by runtime generation, and use `agent_settled` for definitive idle. TUI, RPC, JSON and print are separate modes; `hasUI` does not establish arbitrary TUI support. Native tools call repaired CLI/HTTP/WS operations directly, without an MCP bridge.

Then implement the nine `*-PI` adapters from their real product APIs. Prioritize one contextual stateful client and one streaming/media client after Punt, such as Ethos plus Biff or Lux, to test which small transport helpers can truly be shared. Pi's native `sendMessage` supports useful delivery choices, but Biff/Beadle policy, recipient identity and durable acknowledgements still belong to their engines. Quarry maps native branch entries to the capture contract; it does not read them as Claude JSONL.

Schedule `HOST-PI-DELEGATION` early within P2 so Ethos, PRFAQ, Z-spec and Punt's independent judgment audit are not left waiting at the end. Publish the reviewed supervisor with independent contexts, explicit discovery/grants, lineage, bounded output/time, cancellation and result validation. An ordinary Biff/Punt tool need not install or start that supervisor merely because other workflows require it.

Complete `BEADLE-WORKER-PI` under the shared contained supervisor and the pi portion of `VOX-CALL` under its explicitly controlled-host contract. Both use released native SDK/RPC/JSON capabilities. Pi's trusted extension API provides no OS sandbox; preserve the actual process/container boundary for unattended mail-triggered work. Finish all-nine pi composition and real user journeys, then run mixed OpenCode/pi sessions against the same product daemons to confirm that one integration cannot steal another's state or teardown resources it does not own.

P2 can begin bounded host research and contract review while late P1 work runs if that does not delay the OpenCode commitment. Priority does not require artificial dependencies on the whole OpenCode fleet: a Pi adapter's technical blockers are its own core/host prerequisites. The staffing order remains OpenCode first, and no Pi-only dependency should be placed on an OpenCode release path.

## Codex deferral and the documentation contract

Mark Codex packages, context/queue/capture experiments, worker backends and controlled-voice connectors deferred. Retain their evidence, assumptions, proposed keys and source references. Do not delete existing Codex beads or rewrite closed history. Do not spend the active program on new Codex-specific compatibility probes, packaging or implementation. Generic engine schemas should remain able to represent another harness without prebuilding an unverified Codex mapping.

When the operator reactivates Codex, recheck installed/released versions, plugin packaging, authoritative per-call context, queue delivery and capture fidelity against then-current official source and real stock clients. The September 12 evidence is a starting record, not perpetual certification. Codex's unresolved binding/capture/queue questions explain part of its uncertainty, but the deferral is the operator's priority decision, not a claim that native Codex support is impossible.

For every active task, record the changed public behavior, domain owner, native entry point, state/authority scope, old-bead disposition, prerequisites, acceptance evidence and final artifact. Amend the owning design record before an old “core unchanged” or automatic-install assumption can survive into code. Keep `backlog.json` planning keys distinct from real Beads IDs and apply changes from each repository's directory with the verified mechanics. No adapter is complete solely because its package loads, and no completed OpenCode outcome waits for a deferred Codex checkbox.
