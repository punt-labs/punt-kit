# Bead reconciliation: OpenCode P1 and pi P2

**Priority revision: 2026-09-13.** OpenCode is P1, pi P2, and Codex is deferred. Existing issue priorities/statuses remain the dated audit observations; this document does not mutate them.

The September 12 audit read **2,419 beads** using `bd --readonly list --all --limit 0 --json` with the process working directory set separately to each of the nine repositories. It inspected complete relevant records, including closed prerequisites and operator rulings. No issues, descriptions, statuses, labels or dependency edges were changed.

[backlog.json](backlog.json) preserves **98 researched work packages**: **84 active** and **14 Codex-only deferred**, with **231 active aggregate dependencies** and **18 active certification cells**. Nine additional Codex cells are retained separately as deferred research. These are planning keys, not Beads IDs or an import format. Decompose L/XL work into bounded task sets during implementation.

The schema records `execution_priority`, active `depends_on`, separate deferred history, and independently evaluated `scoped_outcomes`. `KIT-FLEET@opencode` defines P1 completion; `KIT-FLEET@pi` defines P2. An OpenCode outcome cannot require pi-only work or any deferred Codex node. The aggregate task may remain open until both active phases are done. The [original three-host graph](evidence/backlog-2026-09-12.json) is historical evidence.

The [referenced bead snapshot](evidence/referenced-beads.json) preserves exact descriptions, statuses and available dependency data for records used by this plan. The [source baseline](evidence/source-baseline.json) records all nine inventory sizes/revisions. Repository reports contain the authoritative proposed disposition for each cited group; linking an existing bead to several work packages does not authorize closing it several times or replacing its current parent.

## Dependency ownership

`KIT-PROGRAM` coordinates the fleet. Product implementation keeps its existing repository parentage; use tracking links to the coordination epic. Cross-repo blocking links represent actual deliverables, for example:

| Dependent | Required deliverable | Why it blocks completion |

| PRFAQ-MEDIA | Vox/Lux/Quarry operation contracts | Optional-peer composition needs correct session/media/target semantics, without requiring peers for basic PRFAQ. |

| KIT-FLEET | Each product release and KIT-CERTIFY | Fleet completion requires all declared journeys, not merely package registration. |

The active graph does not make all tools depend on Biff. Codex package/context/queue/capture experiments and all Codex adapters/backends have no active edges; they must not be created as P1/P2 blockers when applying this plan. Preserve existing Codex records without falsely closing them. Beadle interactive delivery can finish before its worker backend; full product certification is composite. Its existing custom-WS repair (`BEADLE-TRANSPORT`) remains an aggregate product/program remediation gate, while native stdio/direct-CLI releases can proceed without that unused transport. PRFAQ media tests can use pinned peer contracts and fixtures during development; actual installed-peer journeys are release evidence.

## Apply with the actual Beads mechanics

The September 12 audit observed `bd` **1.0.4 dev main@77e267720368**. At that observation, these nine repositories used one Hosted Dolt `beads` database with different prefixes and directory labels. Repo-scoped working directories are still required. Full cross-repo IDs resolve in that database, so ordinary dependency edges work; no federation or new database is needed. `bd ready` on this version does not honor directory labels automatically: use explicit labels, including **repo:pkit** for punt-kit.

The verified forms and caveats are in [Beads application mechanics](evidence/beads-application.md). During execution:

1. Set process cwd to the owning project. Re-read context, the complete current issue, children, both dependency directions and explicitly labeled ready/list results.
2. Build concrete amendments and new child bodies from the repo report and backlog. Preserve operator rulings, existing status/priority/ownership/parentage unless a specific change is required. Capture each task's expected before/after fields.
3. Amend/reuse matching work. Create only unmatched scopes with the correct repository label and capture returned real IDs. Save a durable `planning key → repository → real ID(s)` map so reruns do not duplicate work.
4. Resolve all prerequisite keys through that map, then add actual blockers. The supported direction is `bd dep add BLOCKED_ID BLOCKER_ID --type blocks`, run from the blocked issue's repo. Add tracking links without reparenting every product epic.
5. Re-read the results, check dependency direction/cycles, preserve existing cycles as separately identified findings, and verify labeled ready queries. Record unapplied or changed scopes. Creating tasks is not evidence of implementation completion.

Use description files with `--body-file` and comment files with `--file` to preserve exact newlines. Always supply the issue ID to `bd update`; omission targets the last touched issue. Preserve labels with `--add-label`. This backlog is **not** validated `bd create --graph` or import input; do not feed it directly to either. There is no assumed `bd split` command: split by creating scoped children and recording the relationship explicitly.

Implementation should begin with the OpenCode P1 host experiments and independently ready core defects identified in [roadmap.md](roadmap.md). The first delivery targets are native OpenCode, beginning with HOST-OPENCODE, shared contracts, finite Punt and the Lux ownership/interaction pilot. Pi-specific host/delegation/adapter work is P2. Core remediation runs in parallel as the roadmap specifies.
