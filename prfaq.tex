\section*{Press Release}

PUNT LABS --- August 2026 --- punt-kit is the kit manager for the Punt Labs
org. It manages four things: the org's \textbf{standards} (author them,
activate them in a repo, audit against them), its \textbf{workflows} (the
11-phase release engine and the playbooks), its \textbf{compliance} checks
(convention audit, PII scan), and --- as the direction it is now building
toward rather than a shipped command --- the \textbf{kit of tools} each repo
runs on. The customer is Punt Labs itself: one operator and the AI agents that
do the work across roughly thirty repositories. External adoption is not a goal
and is explicitly deferred
(see \faqref{faq:what-is-it}, \faqref{faq:external}).

The centerpiece is \texttt{/punt:auto}, and the direction it is headed is a
\textbf{self-prompting engine}: recurring prompts the operator types by hand
become playbooks --- reviewed, versioned programs that generate the prompts
and drive the agent. The executor and six playbooks ship today, the release
engine among them. Turning that into a general engine for loops is the next
investment, committed but not yet built
(see \faqref{faq:self-prompting}).

\prsection{Problem}

Punt Labs is one operator and a roster of AI agents working roughly thirty
repositories. Two costs dominate, and both scale with the number of repos and
sessions rather than with the amount of code.

The first is context. Every agent session starts cold, with no memory of what
came before~\cite{anthropic2025contextengineering}, and the org's conventions
--- how a release runs, what a README must contain, when a PR may merge ---
live in prose that each session has to find. A study of 253 CLAUDE.md files
found these manifests are optimized for code execution rather than
organizational convention: only 8.7\% include security
guidance~\cite{arxiv2509.14744}. Static context files also have no feedback
loop, so nothing notices when a repo has drifted from the document that
describes it~\cite{claudecodememory}. Catching that drift in review is the
expensive path --- a static-analysis vendor puts rote standards checking at
roughly four hours per engineer per
week~\cite{deepsource2025staticanalysis}, which is a figure to treat as
directional, since the vendor is quantifying the pain its own product
removes.

The second is the operator typing the same prompt again. Watching a pull
request to merge, sweeping the backlog, running a release --- these are loops
with named states and guarded transitions, and today the operator re-authors
each one as a fresh cron prompt, once per PR. A hand-typed loop is
unreviewable, unversioned, and evaporates when the session compacts. It is the
same toil the standards corpus removed for conventions, still untouched for
procedure (see \faqref{faq:self-prompting}).

\prsection{Solution}

An org run by agents has to manage two things, and they turn out to be the
same problem. What the org \textbf{knows} --- its conventions, its rules, what
``good'' looks like --- has to reach a session that starts with no memory of
it. What the org \textbf{does} --- its releases, its review loops, its backlog
sweeps --- has to reach that session too, and today it arrives as a prompt
somebody retypes. punt-kit manages both: the standards corpus is the knowing,
the playbooks are the doing, and the four pillars below are how each of them
gets into an agent's hands.

\textbf{Standards.} The corpus is 29 normative prose documents in
\texttt{standards/}, plus per-language coding rules in \texttt{lang-rules/}
that agents auto-load when they touch a matching file. They are prose on
purpose: the consumer is a language model and a human reviewer, and prose is
what both read best. What is machine-checkable is checked separately and
deterministically --- \texttt{punt audit} is
hand-written Python that verifies the org's conventions in a repo (CI
workflows, tool config, permissions, Makefile targets, README SHA pins, plugin
version sync, branch-protection rulesets) and reports each finding with its
rule. \texttt{punt init} scaffolds a new repo that already satisfies them.

\textbf{Tools --- the direction, stated as such.} Punt Labs ships around a
dozen of its own tools, and a repo should be able to say which ones it uses.
\texttt{standards/tool-enable-disable.md} defines how: each tool owns the
vendored zone and the \texttt{enabled} marker of its
\texttt{.punt-labs/<tool>/} subtree, and the host \texttt{CLAUDE.md} carries
exactly one \texttt{@}-import line per enabled tool, so that tool's own guide
composes into every session. \texttt{enable} and \texttt{disable} are the
verbs, and \texttt{disable} is non-destructive.

\emph{What is true today:} the architecture is specified and adopted --- biff,
ethos, and vox each implement \texttt{enable}/\texttt{disable} in their own
CLI, and the markers are committed in nine repos for biff and three for ethos.
\emph{What is not:} punt has no manager command. At v0.11.2 the CLI is
\texttt{init}, \texttt{audit}, \texttt{pii}, \texttt{release}, \texttt{auto},
\texttt{doctor}, \texttt{status}, and \texttt{version} --- there is no
\texttt{punt install} and no \texttt{punt enable}. That surface is the
invested next step, not a shipped one
(see \faqref{faq:kit-manager}, \featureref{feat:kit-manager}).

\textbf{Workflows.} \texttt{punt release} is an 11-phase release engine ---
preflight, version bump, build, release PR, tag, CI wait, GitHub release, PyPI
verification, post-release, cross-repo propagation, and a final verify pass.
It runs on every release, and in the operator's judgment it is the most-used
feature in the org --- judgment rather than measurement, because nothing logs
usage yet (\faqref{faq:metrics}).

\textbf{Compliance.} \texttt{punt audit} and \texttt{punt pii} are the
deterministic checks: convention conformance and a scan for emails, home
directory paths, and hostnames, with a \texttt{--staged} mode for pre-commit.

\textbf{The engine underneath.} \texttt{/punt:auto} runs playbooks: YAML
programs whose steps are either deterministic shell or scoped LLM judgment,
with postconditions and a per-step failure strategy. The executor is an LLM
following \texttt{skills/auto/SKILL.md} --- not a daemon --- which is what lets
a judgment step sit next to a shell step in one program. The release engine is
the shipped proof: eleven deterministic phases with LLM diagnosis on failure.
The drafted next step turns the DSL into a prompt state machine --- named
states, guarded transitions, poll ticks, and persisted run-state with
crash/resume --- so a loop is a reviewed file rather than a retyped prompt
(see \faqref{faq:self-prompting}).

\textbf{Where this is going.} \emph{Shipped today: the CLI and the plugin. The
rest of this paragraph is roadmap, not capability.} The destination is the
engine-and-clients model in \texttt{standards/architecture.md} --- one engine
behind thin client surfaces --- and two of those clients are committed and
unbuilt. An \textbf{MCP server} will expose audit, status, and playbook launch
to any agent runtime, not only Claude Code. A \textbf{REST surface} will serve
CI jobs and dashboards that need findings programmatically. The point of
building both is that the checks and the playbooks do not fork per caller: one
engine answers a human at a terminal, an agent over MCP, and a CI job over
HTTP identically (see \faqref{faq:surfaces},
\featureref{feat:mcp-server}, \featureref{feat:rest-api}).

\prsection{Getting Started}

Install with \texttt{install.sh} (or \texttt{uv tool install punt-kit} if uv is
already present). In a new repo, \texttt{punt init} scaffolds CI workflows,
tool config, permissions, and a \texttt{CLAUDE.md} that references the
standards. \texttt{punt audit} reports where an existing repo diverges.
\texttt{/punt:auto list} shows the playbooks available, and
\texttt{/punt:auto release} runs a release end to end. Nothing phones home;
every command runs locally against the checkout in front of it.

\subsection*{External FAQs}

These are the questions the product's actual users ask --- the operator and the
org's agents. ``External'' here means outward from the tool, not outward from
Punt Labs.

\begin{faqpair}{What is punt-kit and who is it for?}\label{faq:what-is-it}
  punt-kit is the kit manager for the Punt Labs org. It manages four things:
  \textbf{standards} (author them, activate them in a repo, audit against
  them), \textbf{tools} (install them, enable them, compose their guidance into
  a session), \textbf{workflows} (the release engine and the playbooks), and
  \textbf{compliance} (the conformance audit and the PII scan). Its users are
  one operator and the AI agents that work roughly thirty repositories. Two
  surfaces are shipped --- the \texttt{punt} CLI and the
  \texttt{punt@punt-labs} Claude Code plugin --- and two more are committed but
  not yet built: an MCP server and a REST surface
  (see \faqref{faq:surfaces}).
\end{faqpair}

\begin{faqpair}{What does ``kit manager'' mean?}\label{faq:kit-manager}
  A repo declares which of the org's tools it uses, and punt-kit manages that
  declaration. Per \texttt{standards/tool-enable-disable.md}: each tool owns a
  \texttt{.punt-labs/<tool>/} subtree in the repo, an \texttt{enabled} marker
  records the choice, and the host \texttt{CLAUDE.md} carries exactly one
  \texttt{@}-import line per enabled tool --- so the tool's own user guide, not
  a block of managed text, is what lands in the session. \texttt{enable} and
  \texttt{disable} are the verbs, and \texttt{disable} is non-destructive: it
  removes the import and the marker and leaves the subtree dormant.

  The convention is deployed, not theoretical: biff, ethos, and vox each
  implement the verbs in their own CLI, and committed \texttt{enabled} markers
  exist in nine repos for biff and three for ethos. What punt-kit does not yet
  have is the manager surface itself --- there is no \texttt{punt install} and
  no \texttt{punt enable} at v0.11.2. That is the Should Do investment
  (\featureref{feat:kit-manager}), and the press release names this pillar as
  a direction for exactly that reason.

  \textbf{The mechanism is dispatch, not ownership.} When the manager surface
  arrives, \texttt{punt install <tool>} will run that tool's own
  \texttt{install.sh}, and \texttt{punt enable <tool>} will delegate to
  \texttt{<tool> enable}. punt never writes another tool's vendored zone,
  marker, or import line itself. That is not a convenience choice ---
  \texttt{tool-enable-disable.md} \S\,2.2 gives each tool ownership of the
  vendored zone and the \texttt{enabled} marker of its own subtree, and \S\,2.3
  puts the \texttt{enable}/\texttt{disable} verbs on every tool's own CLI. A
  manager that wrote those files directly would be a second writer of state
  the standard assigns to one owner, and would drift the moment a tool changed
  what it deposits. punt-kit's job is to know what the kit is and to call the
  right verb on each member of it.

  One naming point, since the standard already claims the bare form: \S\,2.10
  defines \texttt{punt enable} with no argument as punt enabling \emph{itself}
  in a repo, like any other tool. The manager form takes an argument ---
  \texttt{punt enable <tool>} --- and dispatches.
\end{faqpair}

\begin{faqpair}{How do the standards actually reach an agent?}\label{faq:standards-mechanism}
  Three mechanisms:

  \begin{itemize}[nosep]
    \item \textbf{Reference.} A repo's \texttt{CLAUDE.md} links the standards it
      is bound by; the agent reads the document. 26 of the org's 30
      \texttt{CLAUDE.md} files reference punt-kit today.
    \item \textbf{Auto-load.} \texttt{lang-rules/} holds per-language coding
      rules (Python, Go, C, Swift) that load automatically when an agent touches
      a matching file, scoped by \texttt{paths:} frontmatter.
    \item \textbf{Check.} \texttt{punt audit} is hand-written deterministic
      Python that verifies the conventions a machine can verify --- CI
      workflows, tool config, permissions, Makefile targets, README SHA pins,
      plugin version sync, branch-protection rulesets --- and reports each
      finding with its rule.
  \end{itemize}

  The corpus is prose because its consumers are a language model and a human
  reviewer. Grinding a standard into assertions would lose the rationale that
  makes an agent apply it correctly to a case the rule did not anticipate, and
  the deterministic subset is cheaper to write directly as code.
\end{faqpair}

\begin{faqpair}{What is \texttt{/punt:auto} and why is it the centerpiece?}\label{faq:self-prompting}
  \texttt{/punt:auto} runs \textbf{playbooks}: YAML programs whose steps are
  either \texttt{script} (deterministic shell) or \texttt{llm} (scoped
  judgment), each with an optional postcondition and a failure strategy
  (\texttt{retry}, \texttt{diagnose}, \texttt{abort}). The executor is an LLM
  following \texttt{skills/auto/SKILL.md}, which is why a judgment step can sit
  next to a shell step in one program --- a daemon could not run half of these
  steps. Six playbooks ship today; the release playbook is the proof, running
  the 11-phase engine with LLM diagnosis on failure.

  \textbf{A name collision to fix.} \texttt{punt auto <target>}, the CLI
  subcommand, renders and merges managed sections in project files (Makefile,
  \texttt{settings.json}). \texttt{/punt:auto <playbook>}, the slash command,
  is the playbook executor, and it is the one the self-prompting work builds
  on. They share a word and do unrelated jobs. Naming the collision is not the
  same as resolving it: one of the two should be renamed before the
  state-machine work makes \texttt{auto} load-bearing vocabulary, and that is
  an open call for the operator.

  The investment is turning that DSL into a \textbf{prompt state machine}. The
  drafted design adds named states, guarded transitions (shell checks plus
  scoped LLM-judgment guards for the clauses that are irreducibly judgment),
  \texttt{poll} ticks that compile to a \texttt{/loop} registration, and
  run-state persisted per instance so a machine survives a crash and resumes
  where it stopped. A linear playbook stays valid --- it is the degenerate
  one-state machine.

  What that buys, argued on the one loop we actually run: \textbf{the PR
  watch.} Today the operator re-authors it as a fresh cron prompt for every
  open PR --- twice in one session on 2026-07-27, which is the event that
  motivated the design. As a machine it is a \texttt{watch} state that routes
  to \texttt{fixing} or \texttt{merging} on guards, with the five-clause merge
  gate as the guard on the second edge and \texttt{fixing} ordered first so
  findings never wait. Written as prose in a cron prompt, the current state
  lives only in the model's working context and evaporates on compaction.
  Written as a playbook, it is a reviewed, versioned artifact ---
  \textbf{the tool generates the prompt, and the agent runs the loop}. It is
  also the first conversion target and carries a decision threshold
  (\faqref{faq:next-step}), so this claim gets tested rather than asserted.

  The same three constructs express the backlog sweep (a non-terminating
  machine) and a mission round (a do-while with a review cycle), which is how
  the design checks that the vocabulary generalizes. Names for those playbooks
  --- \texttt{sprint}, \texttt{backlog-cleanup}, and the rest --- are
  illustrative only; the operator wants to debate them and nothing in the
  design depends on the choice.
\end{faqpair}

\begin{faqpair}{How do I get started?}
  Install via \texttt{install.sh}, or \texttt{uv tool install punt-kit} if uv
  is already present. In a new repo, \texttt{punt init} scaffolds CI workflows,
  tool config, permissions, and a \texttt{CLAUDE.md}; it detects the project
  type and is idempotent, so re-running updates without overwriting
  customizations. In an existing repo, \texttt{punt audit} reports what
  diverges. \texttt{/punt:auto list} shows the available playbooks.
\end{faqpair}

\begin{faqpair}{What happens to my data?}
  punt-kit runs locally against the checkout in front of it. It reads
  repository files and, when \texttt{gh} is authenticated, queries the GitHub
  API for repo settings. It transmits nothing to Punt Labs and has no
  telemetry today. That is about to change in one specific way: the operator
  wants \textbf{feature usage logged}, because there is currently no way to
  answer ``which commands does anyone actually run?'' Any such logging is
  local-first and internal-only by default (\featureref{feat:usage-logging}).
\end{faqpair}

\begin{faqpair}{What surfaces exist, and what is coming?}\label{faq:surfaces}
  \texttt{standards/architecture.md} sets the destination: the
  engine-and-clients model, one engine behind thin client surfaces. punt-kit
  is partway there.

  \textbf{Shipped:} the \texttt{punt} CLI, and the \texttt{punt@punt-labs}
  Claude Code plugin that wraps it as slash commands.

  \textbf{Committed, not yet built:} an \textbf{MCP server}
  (\featureref{feat:mcp-server}) exposing audit, status, and playbook launch,
  so an agent running outside Claude Code can call the same checks and start
  the same playbooks; and a \textbf{REST surface}
  (\featureref{feat:rest-api}) so CI jobs and dashboards can read findings
  programmatically rather than scraping CLI output.

  The reason to build both is the property the architecture standard is after:
  the checks and the playbooks do not fork per caller. One engine answers a
  human at a terminal, an agent over MCP, and a CI job over HTTP, and a finding
  means the same thing in all three. They sit in Should Do behind the
  state-machine DSL (\faqref{faq:timeline}) because nothing shipping today
  waits on them --- an ordering call, not a doubt about the destination.
\end{faqpair}

\begin{faqpair}{Can a repo use its own standards or playbooks?}
  Playbooks yes, standards not yet. Playbooks resolve
  project-local first: \texttt{./playbooks/<name>.yaml} shadows the org-wide
  copy, so a repo overrides any playbook by name. The standards corpus is
  currently referenced from punt-kit rather than pointed at a per-repo
  directory --- the engine and corpus are separable in principle but not yet
  parameterized in practice (\featureref{feat:custom-standards}).
\end{faqpair}

\begin{faqpair}{Should anyone outside Punt Labs use this?}\label{faq:external}
  Not today. punt-kit is public --- MIT, on PyPI, on the marketplace ---
  because the org's own tools install it, and public distribution is the
  cheapest way to do that. Whether it fits a team that is not Punt Labs is
  deferred by operator direction until the internal product has found its
  footing (see \faqref{faq:tam}, \faqref{faq:next-step}).
\end{faqpair}

\subsection*{Internal FAQs}

\subsubsection*{Value \& Customer}

\begin{faqpair}{Who is the customer, and what about the market?}\label{faq:tam}
  The customer is Punt Labs: one operator and the org's AI agents, working
  roughly thirty repositories. That is the whole addressable population the
  product is built for.

  \textbf{Market sizing is deferred, deliberately.} punt-kit is an internal
  tool with zero external organizations using it. Sizing a market it is not
  competing in would be an exercise, not a plan --- so the question waits until
  the internal product has found its footing, which is the operator's
  direction (see \faqref{faq:external}).
\end{faqpair}

\begin{faqpair}{What evidence do we have that this is worth building?}\label{faq:customer-evidence}
  \textbf{Internal usage is the evidence now.} It is real, and it is narrow ---
  one org, one operator. Stated plainly:

  \begin{itemize}[nosep]
    \item \textbf{The release engine is exercised on every release.}
      \texttt{punt release} drives all eleven phases, including cross-repo
      propagation into sibling repos, and it is invoked through
      \texttt{/punt:auto release}.
    \item \textbf{The standards corpus is consumed fleet-wide.} 29 normative
      documents, referenced from 26 of the org's 30 \texttt{CLAUDE.md} files,
      plus per-language rules that load automatically on matching files.
    \item \textbf{The enable/disable convention has adopters.} biff, ethos, and
      vox implement it; committed \texttt{enabled} markers exist in nine repos
      for biff and three for ethos --- the convention survived contact with
      three independent implementations.
    \item \textbf{The pain the DSL targets is observed, not hypothesized.} The
      operator hand-authored the same PR watch loop as a fresh cron prompt
      twice in a single session on 2026-07-27. That specific event is what
      motivated the state-machine design.
  \end{itemize}

  \textbf{The context problem is externally corroborated,} which is why the
  standards corpus exists at all: single-file agent manifests ``do not scale
  beyond modest codebases''~\cite{arxiv2602.20478}; a study of 2,303 context
  files found security specified in only 14.5\%~\cite{arxiv2511.12884}; agent
  sessions without context files consume 28.64\% more runtime and 16.58\% more
  tokens~\cite{arxiv2601.20404}.

  \textbf{What is missing:} any evidence from outside Punt Labs. There are no
  external users, no interviews, and no usage data --- not even internal usage
  data, because nothing is logged yet (\featureref{feat:usage-logging}). This
  gap is accepted for now, not closed.
\end{faqpair}

\begin{faqpair}{What are the reference points in this space?}\label{faq:competitors}
  These are tools worth reading, not competitors to beat. punt-kit is not
  competing for adoption right now, so the useful question is which ideas to
  borrow and which scope to stay out of.

  \renewcommand{\arraystretch}{1.4}
  \begin{tabularx}{\linewidth}{@{} l X X @{}}
  \toprule
  \textbf{Tool} & \textbf{What It Does Well} & \textbf{What We Take From It} \\
  \midrule
  projen & Standards-as-code for project config across N
    repos~\cite{projen2024github} & The strongest prior art for cross-repo
    config. We stayed with prose plus deterministic checks rather than a
    TypeScript project model \\
  Backstage & Developer portal with golden-path
    scaffolding~\cite{backstage2025fiveyears} & A warning: it needs a dedicated
    team to run. Scope we deliberately stay out of (\featureref{feat:no-gui}) \\
  Trunk & Metalinter orchestrating 100+
    tools~\cite{trunkio2024codequality} & The linting layer, which punt-kit
    orchestrates rather than reimplements (\featureref{feat:no-linting}) \\
  Copier & Template scaffolding with lifecycle
    updates~\cite{copier2024comparisons} & Idempotent re-templating, which
    \texttt{punt init} approximates \\
  \bottomrule
  \end{tabularx}
  \renewcommand{\arraystretch}{1.0}

  \medskip
  The one thing none of them does is run the org's recurring
  \emph{procedures} as programs that mix deterministic steps with model
  judgment --- which is where punt-kit is investing. That is not a
  differentiation claim; it may simply be a problem only an org run by agents
  has.
\end{faqpair}

\begin{faqpair}{What is the next step to validate the direction?}\label{faq:next-step}
  Internal, and concrete:
  \begin{enumerate}[nosep]
    \item \textbf{Build the state-machine DSL} and convert exactly one
      hand-typed loop --- the PR watch --- into a playbook. One loop, not
      three: if the construct does not carry the loop we run most, it does not
      carry the others.
    \item \textbf{Turn on usage logging}, so the metrics below can be measured
      at all rather than recalled.
    \item \textbf{Watch for six weeks} whether the operator stops typing the
      loop by hand.
  \end{enumerate}
  \textbf{Decision threshold:} if after that window the operator is still
  hand-authoring watch prompts --- because the playbook is harder to invoke,
  or its guards are wrong often enough to distrust --- then the DSL is not the
  leverage, and the investment stops at playbooks as they exist today.
\end{faqpair}

\subsubsection*{Technical}

\begin{faqpair}{What are the major technical risks?}\label{faq:tech-risks}
  \begin{enumerate}[nosep]
    \item \textbf{The executor is an LLM, so machines are not fully
      deterministic.} A shell guard is a pure function of the world and routes
      identically every evaluation; a judgment guard is not, so the same PR
      state can route two ways on two ticks. Mitigation: \texttt{script} is the
      default guard type and \texttt{llm} is opt-in, confined to clauses that
      are irreducibly judgment (``are these findings addressed?''). The trade is
      explicit in the design and is a decision the operator ratifies, not a
      property that leaks in.
    \item \textbf{Ticks are session-scoped.} A \texttt{poll} compiles to a
      \texttt{/loop} registration, which lives in the session that created it
      and dies with it, so a machine pauses when its session ends. Mitigation
      is a documented property rather than machinery: run-state is durable, and
      any \texttt{--resume} invocation re-registers the tick. A paused machine
      loses no state and cannot act wrongly --- it just does not advance.
    \item \textbf{Idempotency is the playbook author's burden.} Crash/resume
      re-visits a state, so an action that already ran must be a no-op the
      second time. The design pushes this onto authors (guard the merge on the
      PR still being open, guard the branch delete on the branch still
      existing). Authors will get it wrong; the mitigation is that guards
      recompute from live state, so a wrong re-visit is usually an empty one.
    \item \textbf{Claude Code API surface.} Plugins, skills, and \texttt{/loop}
      are the substrate the executor stands on, and they evolve. Mitigation:
      punt-kit ships a working plugin and tracks changes as ordinary
      maintenance; the CLI half (\texttt{init}, \texttt{audit}, \texttt{pii},
      \texttt{release}) runs without any of it.
  \end{enumerate}
\end{faqpair}

\begin{faqpair}{What dependencies exist on other teams or systems?}
  \texttt{punt release} depends on GitHub (via \texttt{gh}), PyPI, and on
  sibling repos being checked out locally for cross-repo propagation.
  Distribution depends on PyPI and the Claude Code plugin marketplace.

  The deeper dependency is the playbook executor: it \emph{is} Claude Code
  reading \texttt{skills/auto/SKILL.md}, not a program punt-kit ships. That is
  a deliberate design choice --- half the steps in a real playbook are judgment
  or sub-agent calls that no daemon could run --- but it means playbooks do not
  execute outside a Claude Code session today. The deterministic CLI has no
  such dependency, and the planned MCP server narrows the gap rather than
  closing it: another agent runtime will be able to launch a playbook
  (\featureref{feat:mcp-server}), but the thing executing it is still a
  language model following the protocol, so the dependency becomes ``some
  capable LLM host'' rather than ``Claude Code specifically.''
\end{faqpair}

\begin{faqpair}{What is the development timeline?}\label{faq:timeline}
  \textbf{Shipped, through v0.11.x (August 2026):}
  \begin{itemize}[nosep]
    \item Standards corpus --- 29 documents plus \texttt{lang-rules/} for
      Python, Go, C, and Swift
    \item \texttt{punt init} (scaffold, idempotent, project-type detection),
      \texttt{punt audit}, \texttt{punt pii}, \texttt{punt doctor},
      \texttt{punt status}
    \item \texttt{punt release} --- the 11-phase engine, plus
      \texttt{--resume-from} for restarting at any phase
    \item \texttt{/punt:auto} playbook executor and six playbooks; the Claude
      Code plugin on the punt-labs marketplace
  \end{itemize}

  \textbf{Invested next, in priority order:}
  \begin{enumerate}[nosep]
    \item \textbf{Prompt state-machine DSL} --- states, guarded transitions,
      poll ticks, run-state with crash/resume; convert the PR watch loop as the
      first machine (\featureref{feat:state-machine}).
    \item \textbf{\texttt{punt enable} and \texttt{punt install}} --- the
      kit-manager surface: activate a standard in a repo, install and enable a
      tool, per \texttt{tool-enable-disable.md}
      (\featureref{feat:kit-manager}).
    \item \textbf{Usage logging} --- which commands and playbooks actually get
      run (\featureref{feat:usage-logging}).
    \item \textbf{Audit revival keyed to enabled policy} --- \texttt{punt
      audit} checks a fixed set of conventions today; the revival scopes it to
      what a repo has actually enabled, so a repo is measured against its own
      declared kit (\featureref{feat:audit-revival}).
    \item \textbf{MCP server} --- audit, status, and playbook launch exposed as
      MCP tools, so an agent outside Claude Code can call the same engine
      (\featureref{feat:mcp-server}).
    \item \textbf{REST surface} --- findings over HTTP for CI jobs and
      dashboards (\featureref{feat:rest-api}).
  \end{enumerate}
  Items 5 and 6 complete the engine-and-clients model that
  \texttt{standards/architecture.md} specifies (\faqref{faq:surfaces}). They
  sit behind the first four because every one of those is load-bearing for
  work happening now, while the second client surfaces pay off when something
  outside a Claude Code session needs the engine. That is an ordering call, not
  a doubt about the destination.

  No dates. One operator, agent-executed work, and a queue that reorders on
  the operator's ruling --- a dated plan would be fiction, and the last one
  was.
\end{faqpair}

\subsubsection*{Business}

\begin{faqpair}{Why spend time on an internal tool with no revenue?}\label{faq:revenue-model}
  punt-kit is free and open-source with no paid tiers and no revenue plan. The
  case for the time is internal leverage:
  \begin{itemize}[nosep]
    \item \textbf{It is the substrate the other tools ship on.} biff, quarry,
      vox, and lux all document \texttt{punt release} as their release path.
      Time spent here is amortized across every repo that releases.
    \item \textbf{It is how conventions reach agents at all.} The corpus plus
      the \texttt{@}-import architecture is the delivery mechanism for
      everything the org has decided about how work is done.
    \item \textbf{The DSL investment targets the operator's own time.} Every
      recurring prompt replaced by a playbook is a task the operator stops
      re-deriving from memory.
  \end{itemize}
  \textbf{The risk this leaves open} is opportunity cost: hours on punt-kit are
  hours not spent on the products it serves. The DSL work is the sharpest form
  of that bet (see \faqref{faq:next-step}).
\end{faqpair}

\begin{faqpair}{What are the key metrics for success?}\label{faq:metrics}
  Internal, and chosen so that a bad number means something is actually wrong:
  \begin{enumerate}[nosep]
    \item \textbf{Repos with standards activated} --- how many of the org's
      repos reference the corpus and pass \texttt{punt audit}. Today: 26 of 30
      reference it; conformance is unmeasured.
    \item \textbf{Releases run through the engine} --- the share of releases
      that complete via \texttt{/punt:auto release} without the operator
      dropping to manual steps. Resume-from-phase counts as engine; a hand-run
      merge does not.
    \item \textbf{Recurring prompts replaced by playbooks} --- how many of the
      loops the operator used to type are now files that are actually invoked.
      This is the metric for the DSL investment.
    \item \textbf{Playbook failure mode mix} --- of playbook runs that fail,
      how many are recovered by \texttt{diagnose} versus escalated to the
      operator. Rising escalation means the executor is not carrying its half.
  \end{enumerate}
  \textbf{Caveat, stated up front:} three of these four cannot be measured
  today. There is no usage logging, so ``how many releases ran clean'' is
  currently an act of recall. The metrics are honest only after
  \featureref{feat:usage-logging} lands --- which is why it is on the invested
  list rather than a nice-to-have.
\end{faqpair}

\begin{faqpair}{Why now? What has changed?}\label{faq:why-now}
  Two shifts, one external and one internal.

  \textbf{The work moved to agents.} Nearly all code in this org is now written
  by AI agents in Claude Code sessions, and the agent-context infrastructure
  that makes that governable --- \texttt{CLAUDE.md}, \texttt{@}-imports,
  plugins, skills, hooks --- did not exist eighteen months ago. Standards that
  live only in a senior engineer's head do not reach an agent; standards in a
  document that the session imports do.

  \textbf{The bottleneck moved from writing code to steering loops.} With
  execution cheap, the scarce resource is the operator's attention on which
  loop is running, what state it is in, and whether it may advance. That is
  what makes \texttt{/punt:auto} the centerpiece rather than an automation
  convenience: the loops are now the expensive part, and they are still being
  typed by hand.
\end{faqpair}

\section*{Risk Assessment}

\begin{tabularx}{\textwidth}{@{} l l X @{}}
\toprule
\textbf{\color{SectionBlue}Risk} & \textbf{\color{SectionBlue}Rating} & \textbf{\color{SectionBlue}Assessment} \\
\midrule
Value & \textcolor{RiskRed}{High} &
  \textbf{The whole bet rides on one unproven claim: that a prompt state
  machine beats a well-written prose prompt. Zero machines have run.} The
  design argues the case --- the current state survives compaction, the guards
  are reviewable, run-state resumes after a crash --- but argument is not
  evidence, and authoring a machine costs more than typing the prompt it
  replaces (see the usability row below). The operator asking for a thing is
  not evidence the operator will use it. A Medium rating would average the
  proven shipped half (release engine on every release, corpus referenced by 26
  of 30 \texttt{CLAUDE.md} files) against the unproven investment, and the
  unproven half is what this rating exists to flag. If the guards are wrong
  often enough to be distrusted, the DSL buys nothing and the value is only
  what already ships (see \faqref{faq:next-step}). \\
Usability & \textcolor{RiskAmber}{Medium} &
  The shipped CLI is easy: \texttt{punt init}, \texttt{punt audit},
  \texttt{/punt:auto release}, no configuration. The new surface is not.
  Writing a state machine --- states, ordered guards, idempotent visits --- is
  a harder authoring task than typing the prompt it replaces, and the person
  who must do the authoring is the same operator whose time the feature is
  supposed to save. Authoring cost is paid once per loop and the benefit
  recurs, so the arithmetic works only for loops that genuinely recur. The
  mitigation is to ship one machine for the most-repeated loop and see whether
  it gets used, rather than shipping a library of them. \\
Feasibility & \textcolor{RiskAmber}{Medium} &
  The deterministic half is proven: the CLI ships, the 11-phase release engine
  runs across sibling repos, 210 tests pass. The unproven half is the executor.
  It is a language model following a protocol document, so a judgment guard is
  not reproducible across evaluations, and correct crash/resume depends on
  playbook authors writing idempotent actions. Both are named in the design
  with mitigations (\texttt{script} guards by default; guards recompute from
  live state) rather than assumed away. Nothing depends on unproven
  third-party technology. \\
Viability & \textcolor{RiskGreen}{Low} &
  As an internal tool, viability is not about revenue --- there is none
  planned --- but about whether the org can keep it. It costs one operator's
  attention, it pays for itself on every release it drives, and it has no
  hosting, service, or support obligations. The real exposures are opportunity
  cost (hours here are hours not on the products punt-kit serves) and
  concentration: it is load-bearing for every release in the org and has one
  maintainer. \\
\bottomrule
\end{tabularx}

\section*{Feature Appendix}

Defines the scope boundary. Because most of Must Do already ships, this
appendix does double duty: it records what the product is today, and it names
what is deliberately not being built.

\subsection*{Must Do}

What the product is. Items 1--6 ship today at v0.11.2; item 7 is the one
investment that is essential rather than optional --- without it,
\texttt{/punt:auto} stays a script runner and the self-prompting story is not
true.

Each entry is tagged with the pillar it serves, so the appendix can be checked
against the four-pillar claim. Read the tags and the gap is immediate:
\textsc{tools} appears nowhere in Must Do. That is the honest picture --- the
convention ships, punt's manager surface does not
(\featureref{feat:kit-manager}).

\begin{enumerate}[nosep,leftmargin=2.5em]
  \featureitem{Standards corpus and activation}{\pillar{Standards}29 normative
    prose documents in \texttt{standards/}, plus \texttt{lang-rules/}
    per-language rules (Python, Go, C, Swift) that agents auto-load on matching
    files. A repo activates them by referencing them from
    \texttt{CLAUDE.md}}\label{feat:standards-corpus}
  \featureitem{Deterministic conformance audit}{\pillar{Compliance}\texttt{punt
    audit} --- hand-written checks of CI workflows, tool config, permissions,
    Makefile targets, README SHA pins, plugin version sync, and
    branch-protection rulesets, each finding reported with its
    rule}\label{feat:deterministic-audit}
  \featureitem{Release engine}{\pillar{Workflows}\texttt{punt release} --- the
    11-phase pipeline from preflight through cross-repo propagation and a final
    verify, with \texttt{--resume-from} to restart at any phase. Runs on every
    release in the org}\label{feat:release}
  \featureitem{Playbook executor}{\pillar{Workflows}\texttt{/punt:auto} --- YAML
    programs mixing \texttt{script} (deterministic shell) and \texttt{llm}
    (scoped judgment) steps, with postconditions and per-step failure
    strategies. Cross-repo rollout is a playbook here ---
    \texttt{standards-rollout} and \texttt{permissions-rollout} propagate a
    change across the org}\label{feat:playbooks}
  \featureitem{Compliance scans}{\pillar{Compliance}\texttt{punt pii} ---
    emails, home directory paths, and \texttt{.local} hostnames, with
    \texttt{--staged} for pre-commit}\label{feat:pii}
  \featureitem{The two shipped client surfaces}{\pillar{All four}the
    \texttt{punt} CLI --- \texttt{init}, \texttt{audit}, \texttt{pii},
    \texttt{release}, \texttt{auto}, \texttt{doctor}, \texttt{status},
    \texttt{version} --- and the \texttt{punt@punt-labs} Claude Code plugin
    that wraps them as slash commands. Note that CLI \texttt{auto} and slash
    \texttt{/punt:auto} are different things; see the name collision in
    \faqref{faq:self-prompting}. Two further clients, MCP and REST, are
    committed and sit in Should Do}\label{feat:surfaces}
  \featureitem{Prompt state-machine DSL}{\pillar{Workflows}extend the playbook
    DSL with named states, guarded transitions (shell checks plus scoped
    LLM-judgment guards), \texttt{poll} ticks, and per-instance run-state with
    crash/resume --- turning a hand-typed recurring prompt into a reviewed
    file}\label{feat:state-machine}
\end{enumerate}

\subsection*{Should Do}

Committed work, ordered behind Must Do because nothing shipping today waits on
it. Two kinds of item: the pieces that complete the kit-manager identity ---
the manager surface, usage logging, an audit scoped to what a repo enables ---
and the client surfaces the engine-and-clients model in
\texttt{standards/architecture.md} calls for, MCP and REST.

\begin{enumerate}[nosep,leftmargin=2.5em]
  \featureitem{Kit-manager surface}{\pillar{Tools}\texttt{punt install <tool>}
    runs that tool's own \texttt{install.sh}; \texttt{punt enable <tool>} delegates to
    \texttt{<tool> enable}, and \texttt{disable} likewise. Dispatch, not
    ownership: punt never writes another tool's vendored zone, marker, or
    import line, because \texttt{tool-enable-disable.md} \S\,2.2 gives those to
    the tool and \S\,2.3 puts the verbs on the tool's own CLI. The bare
    \texttt{punt enable} stays punt enabling itself,
    per \S\,2.10}\label{feat:kit-manager}
  \featureitem{Usage logging}{\pillar{All four}record which commands and
    playbooks actually run, locally and internal-only, so the metrics in
    \faqref{faq:metrics} are measured rather than
    recalled}\label{feat:usage-logging}
  \featureitem{Audit revival keyed to enabled policy}{\pillar{Compliance +
    Tools}scope \texttt{punt audit} to what a repo has actually enabled, so
    each repo is measured against its own declared kit instead of one fixed
    list of conventions}\label{feat:audit-revival}
  \featureitem{Reconcile on the new engine}{\pillar{Standards}\texttt{/punt:reconcile}
    --- LLM-driven reconciliation of a repo against changed standards, rebuilt
    as a playbook rather than a standalone prompt}\label{feat:reconcile}
  \featureitem{Autopilot as a state machine}{\pillar{Workflows}the autonomous
    backlog loop reborn as a non-terminating machine with guarded transitions,
    replacing today's prose loop playbook}\label{feat:autopilot}
  \featureitem{Custom standards directory}{\pillar{Standards}parameterize the
    corpus location so a repo can point at its own rules. Separable in
    principle today, not parameterized in
    practice}\label{feat:custom-standards}
  \featureitem{MCP server}{\pillar{All four}expose audit, status, and playbook
    launch as MCP tools over the same engine the CLI calls, so an agent running
    outside Claude Code gets identical checks and can start the same playbooks
    (\faqref{faq:surfaces})}\label{feat:mcp-server}
  \featureitem{REST surface}{\pillar{All four}HTTP access to audit findings and
    run status for CI jobs and internal dashboards, so a pipeline reads
    structured results instead of scraping CLI output}\label{feat:rest-api}
\end{enumerate}

\subsection*{Won't Do}

Boundaries someone could reasonably expect punt-kit to cross, and the reason
it does not. For the first four, another tool owns the job and punt-kit
integrates with it instead.

\begin{enumerate}[nosep,leftmargin=2.5em]
  \featureitem{GUI or web dashboard}{punt-kit ships no user interface of its
    own --- a web front end would split focus and target a different user, and
    teams that want a portal should use Backstage. This is consistent with the
    planned REST surface (\featureref{feat:rest-api}): punt-kit serves findings
    to somebody else's dashboard; it does not build
    one}\label{feat:no-gui}
  \featureitem{CI system replacement}{punt-kit generates and validates CI
    workflows. It does not replace GitHub Actions, GitLab CI, or any CI
    runner}\label{feat:no-ci}
  \featureitem{Code parsing or linting}{punt-kit orchestrates linters (ruff,
    mypy, shellcheck) and validates their configuration. It does not parse
    source code. Teams that want a metalinter should use Trunk or
    MegaLinter}\label{feat:no-linting}
  \featureitem{Package management}{validates distribution config and automates
    release pipelines; does not replace PyPI, npm, or
    uv}\label{feat:no-package-mgmt}
  \featureitem{External adoption machinery}{no marketing site, no onboarding
    path for non-Punt-Labs teams, no third-party standards packs. Deferred by
    operator direction until the internal product has found its footing
    (\faqref{faq:external})}\label{feat:no-adoption}
\end{enumerate}
