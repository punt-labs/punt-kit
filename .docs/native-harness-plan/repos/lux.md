## Mandatory remediation

**LUX-CONTEXT: explicit native session and runtime ownership.** Extend the existing identity substrate so transport kind, harness session, process/connection epoch, agent identity, repo/worktree and applet program are explicit fields with clear lifetime rules. Preserve stable logical ownership across reconnect, add a physical connection epoch for diagnostics, and keep actual PID as optional diagnostic data. `AppletIdentity.for_session(program, session_pid)` and `ClientIdentity` currently encode/parse a four-part display name to obtain a PID for menu grouping. This is the seam to remove; do not encode Codex thread IDs or pi UUIDs into fake PIDs or pretend a direct pi client is an MCP session. Amend `lux-fh49` from a choice of PID conventions into explicit owner-vs-process fields. Reuse existing Hub sessions, leases, last-peer cleanup and successor protections. [Applet identity](https://github.com/punt-labs/lux/blob/23867ae87b1112753e37906e3d595a8e1ad647fd/src/punt_lux/applets/identity.py#L43), [name parser invariant](https://github.com/punt-labs/lux/blob/23867ae87b1112753e37906e3d595a8e1ad647fd/src/punt_lux/domain/hub/client_identity.py#L129), [lease policy](https://github.com/punt-labs/lux/blob/23867ae87b1112753e37906e3d595a8e1ad647fd/src/punt_lux/domain/hub/session_lease.py#L27).

**LUX-LIFETIME: close real successor/callback gaps.** Address open `lux-qbtv` (subscribe can bind a successor's handler; predecessor can throw after successor teardown), `lux-tfn1` (cross-program callback overwrite) and `lux-6chc` (reconnect epoch) while adding new clients. Preserve closed `lux-95zt` same-key MCP teardown accounting and the current bounded inbox/lease cleanup improvements. Model-owned scene lifetime, session applet lifetime, repo-owned boards and global app music scenes are different product choices; native disconnect must follow those choices rather than deleting every scene or retaining every menu. Treat fork/reopen as explicit ownership transitions with lineage.

**LUX-ENABLE: ship `lux-yy7s` before uniform harness activation.** Current `enable`/`disable` write `display:y/n` in `.punt-labs/lux.md`; path resolution is cached for a whole process and points at the main repo root via `git-common-dir`. That is not the common marker and is wrong as an implicit resolver for a server hosting multiple cwd/session contexts. Introduce `.punt-labs/lux/enabled`, explicit repo resolution and native guidance projection while preserving the intended worktree policy. Decide/document whether display preference remains repo-default or per-session preference; do not confuse turning one session off with stopping a shared display. The old Claude guidance can remain a generated Claude projection, while AGENTS/skills use native formats. [Current enablement](https://github.com/punt-labs/lux/blob/23867ae87b1112753e37906e3d595a8e1ad647fd/src/punt_lux/__main__.py#L55), [cached config path](https://github.com/punt-labs/lux/blob/23867ae87b1112753e37906e3d595a8e1ad647fd/src/punt_lux/config.py#L31).

**LUX-CLIENT-CONTRACT: publish a small TS HTTP/WS client boundary.** The existing Python facade and typed operations are the canonical behavior. Generate/check JSON schemas and REST/WS request/result types; add explicit endpoint discovery, capability/version negotiation, cancellation, bounded receive, reconnect/on_connect re-registration, and equivalent identity header encoding. A CLI JSONL listener can be added only if justified for Python reuse; native TS direct REST/WS is already a natural supported front door. Fix eager package-root imports (`lux-teyq`) so Python library consumers do not pull in the entire Hub process graph. Do not resurrect public `LuxRestClient`: closed `lux-duqj` intentionally hid it.

**LUX-NATIVE-UX: own interactions in the correct runtime.** A registered callback requires a held listen leg and identification; polling callback counts cannot satisfy an immediate menu click. The actual `callback_register` gate and real WS tests already enforce this. Native adapter/app clients should directly handle deterministic reopen/raise/controls, and enqueue a typed origin-tagged message only for interactions requiring model work. Keep the display's native frame raising distinct from a delayed agent response. Closed `lux-m3xr` already fixed frame binding/unified dispatch; do not implement that again. [Callback gate](https://github.com/punt-labs/lux/blob/23867ae87b1112753e37906e3d595a8e1ad647fd/src/punt_lux/operations/callbacks.py#L84), [WS round-trip tests](https://github.com/punt-labs/lux/blob/23867ae87b1112753e37906e3d595a8e1ad647fd/tests/client/test_ws_e2e.py#L102).

Preserve existing loopback Host/Origin policy and cross-host Hub/Display trust work. `ClientIdentity` is intentionally not authentication under the local trust model; adding harness support does not justify inventing an enterprise authorization system. Conversely do not expose its loopback HTTP endpoints publicly for a remote OpenCode server: route through an explicitly supported local adapter or the established cross-host architecture with its current trust contracts. [Loopback policy](https://github.com/punt-labs/lux/blob/23867ae87b1112753e37906e3d595a8e1ad647fd/src/punt_lux/transport_policy.py#L19).

## Native harness designs

**Codex (deferred):** a native Codex plugin packages MCP/skills and actual Codex lifecycle handlers. Reuse daemon streamable HTTP for model operations only after the shared context-binding spike proves per-thread/child ownership; an OpenAI MCP connection is not automatically one Lux owner. A native lifecycle-owned companion may hold the WS/app callback leg, but it receives explicit session context from a proven channel and uses leases/cleanup, never process-grandparent detection. Skills construct useful scene trees and invoke native tool names; no expectation that `/lux:scene.beads` exists in Codex. Codex has no established arbitrary plugin TUI widget API, so external Lux remains the visual output surface. Native hook context/Stop feedback or a separately validated queue path handles agent-required actions; routine menu reopening remains immediate in Lux and cannot depend on experimental wake support.

**OpenCode:** publish an npm server plugin with typed native tools that pass `sessionID`, agent, directory/worktree into REST/WS calls. Prefer this explicit context path for stateful scene/menu ownership over a shared MCP connection; generic safe introspection can still reuse MCP where appropriate. Maintain per-session clients inside the potentially shared plugin instance. A separate native TUI export shows display connection/status, scene controls and direct menu actions, using current slots/keymap/dialog APIs and disposal. Server session lifetime and TUI attach lifetime must not be conflated. Use SDK session messages for agent-needed interactions with receipts/deduplication. A Lux renderer is not an OpenCode browser/webview; no generic MCP Apps renderer is assumed.

**Pi:** publish a pi package with TS tools/commands, scene-composition skills and keyed TUI status. Use direct REST and WS with a genuine pi identity; no MCP bridge. Start connections after session_start, close on session_shutdown, reconstruct branch-sensitive ownership on session_tree, and re-register on reconnect. Native `registerTool` results explain scene IDs and errors; `sendMessage` carries origin-tagged user interaction data when model work is needed. Use TUI dialogs/components only for controls that fit the terminal; Lux still owns rendering. Handle `ctx.mode === "rpc"` separately because hasUI is true but custom TUI is unavailable. Experimental pi overlay UI is optional, not a core dependency.

Codex certification is deferred. Target OpenCode 1.18.30 (1.18.27 compatibility candidate), and pi 0.85.1 (0.84.4 candidate). Native support must work without Claude installed/configured. Use the master command manifest for consistent semantics, with true harness-specific invocations and permission behavior.

## Product acceptance journeys

For each native harness, create a real interactive scene, inspect Hub state and actual painted geometry/screenshot, click a control, close/minimize a frame and reopen it from the owned menu. Confirm the current agent appears under Clients with correct repo/session/app details. Repeat with two concurrent sessions in one repo, another worktree, multiple applets and Vox music already present. Scene state must remain Hub-authoritative; the native TUI is only another controller.

Disconnect one transport leg, reconnect with the same logical identity/new epoch, race predecessor and successor subscription, kill the harness, restart Hub and Display independently, change session/fork, compact and disable. Verify expected persistent scenes survive, ephemeral owners/menus expire, and no callback goes to a different owner. Exercise absent Hub, absent Display, denied native operation, untrusted project configuration, malformed scene/schema, non-ASCII labels and wrong protocol version. CLI JSON/error tests must parse the actual output channel until normalized.

Retain existing operation/REST parity, identity, session cleanup, lease, callback and real WS tests; run isolated Hub/Display instances and the existing integration display harness, never the operator's live Hub. Unit and WS tests alone do not show correct visual rendering, menu behavior or TUI integration: every lane needs the real entry-point journey and recorded introspection/screenshot evidence. Current Claude hooks/MCP/applets must pass the same ownership/regression paths after the core migration. Pending upstream context/wake/UI limitations are release gates for the features that need them, not reasons to pretend a shim is first-class support.
